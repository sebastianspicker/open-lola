# Research To Requirements Process

Date: 2026-05-04
Status: clean-room translation process
Verdict: PARTIAL

## Purpose

This process prevents internal reverse-engineering notes from becoming source
code, public protocol docs, or copied implementation behavior.

Every research-derived task must pass through four layers:

1. Internal observation.
2. Engineering requirement.
3. Clean implementation.
4. Public documentation.

The engineering requirement layer must use a stable `CRQ-*` ID from
[clean-room-requirement-ledger.md](clean-room-requirement-ledger.md). If no ID
exists, create the requirement entry before source code, tests, or public docs
are changed.

## Required Template

| Field | Required content |
|---|---|
| Requirement ID | `CRQ-*` identifier from the clean-room requirement ledger. |
| Internal observation | Short private note, evidence label, internal source artifact, and confidence. No raw strings or code in public docs. |
| Engineering requirement | Vendor-neutral behavior open-lola must achieve independently. |
| Clean implementation | Original implementation plan using public APIs, standards, own measurements, and own tests. |
| Public documentation | Sanitized architecture-level wording and confidence label. |
| Validation task | Test, fixture, measurement, or release gate that proves the requirement. |
| Reviewer | Maintainer or clean-room reviewer for normal work; maintainer, clean-room reviewer, and legal reviewer for compatibility work. |

## Examples

| Internal observation | Engineering requirement | Clean implementation | Public documentation |
|---|---|---|---|
| Internal static analysis suggests media and control are separated. | Keep media transport independent from session/control. | Implement open-lola session JSON and native UDP PCM as separate modules with independent tests. | "Media and control are separate open-lola lanes." |
| Internal evidence suggests low buffering is central. | Fastest mode must use the lowest measured stable receive target. | Implement explicit latency profiles and reject hidden buffering in PASS reports. | "Direct Audio First is measurement-gated and audio-latency first." |
| Internal evidence suggests video is subordinate to audio. | Video must degrade before audio playout target changes. | Add video pressure policy and tests that reject audio latency changes. | "Video is best-effort and cannot change fastest audio defaults." |
| Internal evidence suggests compatibility is not proven. | Compatibility must stay optional and evidence-gated. | Add a deferred compatibility ledger; do not enable peer compatibility by default. | "Legacy compatibility remains PARTIAL until authorized peer tests exist." |
| Public Blackmagic documentation describes SDK availability. | Blackmagic-specific support must be optional. | Keep generic AVFoundation path buildable without Desktop Video SDK. | "Blackmagic hardware can be tested through public macOS capture surfaces first." |
| Public Art-Net site states credit/OEM-code expectations. | Lighting output must record standards and attribution disposition. | Require report fields for protocol, credit, OEM-code status, and isolated network. | "Lighting protocols are gated by standards review and required acknowledgements." |

## Conversion Rules

- Requirement IDs are assigned in
  [clean-room-requirement-ledger.md](clean-room-requirement-ledger.md).
- A requirement cannot contain recovered function names, raw strings, offsets,
  byte counts, or packet grammar from internal RE evidence.
- A requirement can contain behavior goals: latency target, isolation, bounded
  callback work, degradation policy, validation gate.
- If a requirement needs exact interoperability, it must be marked
  `requires validation` and cannot become public compatibility language until
  authorized runtime captures and tests exist.
- If evidence is only static, the public claim must be `inferred`,
  `hypothesis`, or `requires validation`.
- If evidence is generated by open-lola tests or measured runs, the public claim
  may be `confirmed` after reviewer approval.
- Compatibility parser or packet work must pass
  [compatibility-work-gate.md](compatibility-work-gate.md) before source
  implementation.

## Promotion Checklist

- [ ] Internal observation has a source artifact.
- [ ] Evidence label is present.
- [ ] `CRQ-*` requirement ID is present.
- [ ] Requirement is vendor-neutral or public-standard based.
- [ ] Implementation plan uses original code and public APIs.
- [ ] Test fixture provenance is recorded in
      [fixture-provenance.md](fixture-provenance.md).
- [ ] Public wording omits raw RE detail.
- [ ] Reviewer approves the translation.
