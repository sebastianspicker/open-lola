# UltraGrid and JackTrip Connector Gap Audit Draft

Date: 2026-05-18
Status: draft audit from current dirty worktree
Verdict: PARTIAL

## Scope

This draft records what is still missing for full Swift-native UltraGrid/MVTP
and JackTrip connectors, using the current repository state and current public
protocol references.

Inspected repo areas:

- `Sources/OpenLolaCore/Connectors/UltraGrid/`
- `Sources/OpenLolaCore/Connectors/JackTrip/`
- `Sources/OpenLolaCore/Connectors/Core/`
- existing LoLa live CoreAudio/AVFoundation bridge surfaces
- focused connector tests under `Tests/OpenLolaCoreTests/`
- `docs/current-state.md`, `docs/source-contracts.md`, and `scripts/README.md`

Public references checked:

- UltraGrid packet types:
  `https://raw.githubusercontent.com/wiki/CESNET/UltraGrid/UltraGrid-packet-types.md`
- UltraGrid packet-format index:
  `https://github.com/CESNET/UltraGrid/wiki/Development#packet-formats`
- UltraGrid NAT traversal:
  `https://github.com/CESNET/UltraGrid/wiki/NAT-traversal`
- JackTrip network protocol:
  `https://raw.githubusercontent.com/jacktrip/jacktrip/main/docs/Documentation/NetworkProtocol.md`
- JackTrip packet header:
  `https://raw.githubusercontent.com/jacktrip/jacktrip/main/src/PacketHeader.h`

## Current State

The current dirty worktree has meaningful first-slice connector work:

- `.mvtpUltraGrid` now plans as `internalUltraGridMvtp`, and the session runner
  calls `UltraGridCompatibilityRunner` instead of making `uv` the primary
  runtime.
- `.jackTrip` now plans as `internalJackTripAudio`, and the session runner calls
  `JackTripCompatibilityRunner` for the primary audio path.
- UltraGrid has RTP packet typing, PT 20 raw-video fragment payload support,
  PT 21 PCM audio payload support, unsupported-mode reporting, memory/socket
  transmit/receive surfaces, and a media report model.
- JackTrip has DEFAULT header encode/decode, planar/int16 conversion, UDP socket
  TX/RX surfaces, stop-control datagram filtering, basic sequence analysis, and
  a media report model.
- Focused tests cover codec round trips, malformed packet rejection, simple
  unsupported-mode rejection, memory-runner reports, and launch-plan/session
  routing.

This is not yet a full connector. The implementation remains source-level and
bounded. Report text still says real interoperability remains `PARTIAL` until
measured peer capture evidence exists.

## UltraGrid Missing Work

### UG-01: Native media input is synthetic, not CoreAudio or AVFoundation

- Severity: P1
- Category: Runtime correctness / evidence boundary
- Subsystem: UltraGrid native media runner
- File: `Sources/OpenLolaCore/Connectors/UltraGrid/UltraGridCompatibility.swift`
- Evidence: `UltraGridCompatibilityRunner.buildDatagrams` currently creates
  zero-filled PCM with `Data(repeating: 0, ...)` and generated video bytes
  capped at `4_096` bytes, then packetizes those payloads.
- Why it matters: the plan says Open LoLa should use Mac-native CoreAudio,
  MADI/direct audio, AVFoundation video, UDP sockets, timing, and report
  infrastructure. Current UltraGrid TX only proves synthetic packet shape.
- Runtime/user impact: a user can get a native report without proving that
  actual audio or video device samples entered the UltraGrid packet stream.
- Suggested remediation: add UltraGrid live media providers analogous to the
  LoLa live paths: CoreAudio capture/playback for audio blocks and generated or
  AVFoundation raw-frame providers for video.
- Verification required: focused tests with injectable audio/video providers;
  one local socket run proving provider payload bytes arrive in encoded RTP;
  no `PASS` without measured peer evidence.
- Suggested test: inject deterministic audio/video providers whose byte pattern
  is not generated by the runner, then assert received UltraGrid datagrams decode
  to those bytes.
- Risk of change: high, because live capture and pacing touch realtime and UDP
  paths.
- Confidence: high

### UG-02: RX has no sequence, timestamp, loss, jitter, duplicate, or reorder validation

- Severity: P1
- Category: Runtime correctness
- Subsystem: UltraGrid RTP receive
- File: `Sources/OpenLolaCore/Connectors/UltraGrid/UltraGridCompatibility.swift`
- Evidence: `UltraGridCompatibilityMediaReport` contains `rtpPacketsLost`, but
  the runner never computes it. `UltraGridSocketMediaReceiver` decodes packets
  and appends them; it does not validate RTP sequence continuity, timestamp
  steps, SSRC stability, duplicates, out-of-order packets, jitter, or per-stream
  loss.
- Why it matters: public UltraGrid compatibility depends on RTP/MVTP behavior,
  not just payload type acceptance. Loss/reorder/timing are explicit high-risk
  runtime areas in this repo.
- Runtime/user impact: a report can say the bounded run is `partial` while
  hiding important media-quality failures.
- Suggested remediation: add a per-stream UltraGrid receive analyzer that tracks
  SSRC, sequence, timestamp, missing packets, duplicate packets, out-of-order
  packets, late packets, and frame reassembly failures.
- Verification required: unit tests for normal sequence, gap, duplicate,
  reorder, timestamp mismatch, SSRC mismatch, and partial video frame reassembly.
- Suggested test: feed synthetic datagrams with sequence gaps and assert report
  counters and verdict/runtime error reflect the failure.
- Risk of change: medium.
- Confidence: high

### UG-03: Real UltraGrid peer interoperability is unproven

- Severity: P1
- Category: Compatibility evidence
- Subsystem: UltraGrid parity and field validation
- File: `scripts/README.md`, `Sources/OpenLolaCore/Connectors/UltraGrid/`
- Evidence: scripts describe Docker/native UltraGrid reference/parity helpers,
  but the focused Swift tests use memory receivers and local codec assertions.
  The report boundary says measured UltraGrid peer capture evidence is still
  required.
- Why it matters: the public UltraGrid packet-type docs identify PT 20/PT 21 and
  other RTP modes, but source-level packet creation is not proof that public
  UltraGrid accepts and renders/plays the stream.
- Runtime/user impact: native reports can be mistaken for interoperability
  success.
- Suggested remediation: add a repeatable parity lane that runs Swift-native TX
  into real UltraGrid RX and real UltraGrid TX into Swift-native RX, capturing
  packet evidence, UltraGrid logs, report JSON, and validation output.
- Verification required: Docker/native UltraGrid parity scripts must produce
  machine-readable evidence and keep verdict `PARTIAL` until field thresholds
  are defined and met.
- Suggested test: non-network unit tests for parser/report validation plus a
  script-level smoke that is skipped unless a reviewed UltraGrid binary/image is
  configured.
- Risk of change: medium.
- Confidence: high

### UG-04: Codec and mode coverage is intentionally narrow

- Severity: P2
- Category: Protocol coverage
- Subsystem: UltraGrid RTP/MVTP codec
- File: `Sources/OpenLolaCore/Connectors/UltraGrid/UltraGridRTPPacketCodec.swift`
- Evidence: only PT 20 and PT 21 classify as supported. FEC, encryption, JPEG,
  H.264/dynamic RTP, G.711, and other packet types are rejected or grouped as
  unsupported.
- Why it matters: this matches the first-slice plan, but it is not a full
  UltraGrid connector. UltraGrid public docs list PT 22, 24, 25, 27, 28, 29 and
  compatible mode types 0, 8, 26, 96, 97.
- Runtime/user impact: users selecting common compressed, encrypted, FEC, or
  compatible modes will not interoperate.
- Suggested remediation: keep unsupported modes explicit, then add one mode at a
  time only after public packet evidence and tests exist.
- Verification required: mode-specific encode/decode fixtures from public docs
  or measured UltraGrid captures.
- Suggested test: for each new mode, add byte-level fixtures and failure tests
  for malformed payloads.
- Risk of change: high for FEC/encryption/codec-specific modes.
- Confidence: high

### UG-05: NAT/server-client behavior is not implemented

- Severity: P2
- Category: Network compatibility
- Subsystem: UltraGrid session topology
- File: `Sources/OpenLolaCore/Connectors/UltraGrid/UltraGridLaunchPlan.swift`,
  `Sources/OpenLolaCore/Connectors/UltraGrid/UltraGridCompatibility.swift`
- Evidence: the native plan carries `native-mvtp`, `--peer`, and port metadata,
  while the socket runner sends to a configured peer and filters received packets
  by configured peer. It does not implement UltraGrid `--server` / `--client`
  semantics, receiver-learned endpoints, keepalive behavior, bind-address
  options, or STUN/NAT-PMP/PCP behavior.
- Why it matters: the UltraGrid NAT docs describe server/client and UDP
  hole-punching behavior, including default video/audio ports 5004/5006.
- Runtime/user impact: native Open LoLa may fail in topologies where public
  UltraGrid works through its server/client NAT mode.
- Suggested remediation: define first-slice topology explicitly as direct peer
  only, then add a server/client endpoint state machine after peer parity passes.
- Verification required: local two-process tests for peer-learned endpoint
  updates and fixture tests for command/report topology fields.
- Suggested test: receiver starts without a peer, learns the first sender
  address, then sends subsequent outbound datagrams to that learned endpoint.
- Risk of change: medium.
- Confidence: medium

### UG-06: Raw video frame sizing and fragmentation are not field-realistic yet

- Severity: P2
- Category: Media correctness
- Subsystem: UltraGrid video payloads
- File: `Sources/OpenLolaCore/Connectors/UltraGrid/UltraGridCompatibility.swift`
- Evidence: `buildDatagrams` computes a configured frame byte count but then
  uses only `min(videoPayloadByteCount, 4_096)` generated bytes. Large real
  frames, MTU pressure, pacing, and full-frame reassembly under loss are not
  exercised.
- Why it matters: first-slice raw video will be bandwidth-heavy; a 4 KiB payload
  does not validate real 640x360 or larger frame fragmentation behavior.
- Runtime/user impact: reports understate actual packet count, bandwidth, CPU,
  and reassembly risks.
- Suggested remediation: use real configured frame size for generated raw-video
  tests when explicitly requested, and add bounded stress tests around packet
  count, MTU, and frame reassembly.
- Verification required: tests for full frame byte counts, oversized frame
  rejection/fragmentation, and report byte counters.
- Suggested test: 640x360 RGB generated frame should produce the expected
  fragment count and reassemble exactly.
- Risk of change: medium.
- Confidence: high

## JackTrip Missing Work

### JT-01: Native audio input is synthetic, not CoreAudio/JACK/MADI

- Severity: P1
- Category: Runtime correctness / evidence boundary
- Subsystem: JackTrip native audio runner
- File: `Sources/OpenLolaCore/Connectors/JackTrip/JackTripCompatibility.swift`
- Evidence: `JackTripCompatibilityRunner.buildDatagrams` calls
  `syntheticInterleavedPCM`, converts it to planar int16, and sends that.
- Why it matters: the connector currently proves packet shape, not live audio
  capture/playback. The public JackTrip protocol is a realtime audio stream.
- Runtime/user impact: a native report can be produced without any hardware path
  or audible loopback.
- Suggested remediation: add a JackTrip CoreAudio live bridge or general
  connector audio provider that can reuse the existing direct realtime audio
  graph where practical.
- Verification required: injectable provider tests, CoreAudio preflight tests,
  and one local socket loop that proves decoded JackTrip payload reaches a
  playback/enqueue boundary.
- Suggested test: inject a non-synthetic interleaved PCM pattern, assert the
  encoded planar payload matches, decode it through RX, and assert playback
  enqueue receives the same audio block.
- Risk of change: high.
- Confidence: high

### JT-02: JackTrip channel sentinel behavior is not modeled

- Severity: P1
- Category: Protocol correctness
- Subsystem: JackTrip DEFAULT header
- File: `Sources/OpenLolaCore/Connectors/JackTrip/JackTripProtocolModel.swift`
- Evidence: `JackTripDefaultHeader.validate` rejects zero incoming/outgoing
  channel fields. The public JackTrip protocol notes that the outgoing channel
  field may be `0` when in/out counts match and `0xff` when there are zero audio
  interface input channels.
- Why it matters: this is a documented compatibility detail, not an optional
  advanced mode.
- Runtime/user impact: Open LoLa may reject or fail to emit valid JackTrip
  DEFAULT packets from real peers.
- Suggested remediation: update header validation and payload length resolution
  to handle documented channel sentinels without accepting ambiguous malformed
  packets.
- Verification required: byte-level tests for normal channel counts, outgoing
  `0`, outgoing `0xff`, malformed zero incoming, and payload-size inference.
- Suggested test: decode a DEFAULT packet with outgoing channel count `0` and
  verify payload channel count resolves from incoming/local negotiated channels.
- Risk of change: medium.
- Confidence: high

### JT-03: Redundancy framing is not implemented

- Severity: P1
- Category: Protocol correctness / loss behavior
- Subsystem: JackTrip UDP datagram framing
- File: `Sources/OpenLolaCore/Connectors/JackTrip/JackTripCompatibility.swift`,
  `Sources/OpenLolaCore/Connectors/JackTrip/JackTripLaunchPlan.swift`
- Evidence: the plan carries `--jacktrip-redundancy`, and launch-plan facts say
  redundancy is modeled as bounded packet copies, but the runner emits one
  `JackTripAudioPacket` per datagram. Public JackTrip docs say redundancy
  concatenates `R` full packets in a single UDP datagram, newest first.
- Why it matters: redundancy affects wire format and loss recovery. Treating it
  as a report/config field is not compatible with JackTrip peers using `-r`.
- Runtime/user impact: native Open LoLa will not match JackTrip redundancy mode
  and cannot validate recovery behavior.
- Suggested remediation: add a `JackTripUdpDatagram` layer that can carry one or
  more full packets, implement redundancy TX, and implement RX scan/revival
  behavior.
- Verification required: encode/decode tests for redundancy factor 1, 2, and
  larger; missing-sequence recovery tests; malformed concatenation tests.
- Suggested test: with redundancy `3`, datagram `n` contains packets
  `[n, n-1, n-2]`; RX missing `n-1` revives it from the next datagram.
- Risk of change: medium-high.
- Confidence: high

### JT-04: P2P server peer learning is incomplete

- Severity: P1
- Category: Network compatibility
- Subsystem: JackTrip socket runner
- File: `Sources/OpenLolaCore/Connectors/JackTrip/JackTripCompatibility.swift`,
  `Sources/OpenLolaCore/Connectors/JackTrip/JackTripLaunchPlan.swift`
- Evidence: public JackTrip P2P server mode waits for the first UDP datagram and
  uses its source address/port as the peer endpoint. The current runner filters
  by configured peer and transmits to configured `peerAudioPort` or local
  `audioPort`.
- Why it matters: direct JackTrip P2P behavior is peer-discovery based; requiring
  a pre-known peer port is weaker than the public behavior.
- Runtime/user impact: native Open LoLa can fail in normal JackTrip server/client
  pairing where the peer source port is learned at runtime.
- Suggested remediation: add a receiver-side endpoint learning state and a
  bidirectional runner that sends responses to the learned source endpoint.
- Verification required: two local UDP socket tests for server learns client
  source port and tx-rx routes subsequent packets to that endpoint.
- Suggested test: launch RX with `peer == ""` or wildcard, send one packet from
  an ephemeral client socket, assert the runner records and uses the observed
  source port.
- Risk of change: medium.
- Confidence: high

### JT-05: Hub, TCP handshake, authentication, WebRTC, and WebTransport are absent

- Severity: P2
- Category: Protocol coverage
- Subsystem: JackTrip advanced deployment modes
- File: `Sources/OpenLolaCore/Connectors/JackTrip/JackTripProtocolModel.swift`
- Evidence: unsupported modes include hub, WebRTC, WebTransport, JamLink,
  empty-header, JACK graph, plugins, and non-PCM audio. Public JackTrip docs
  include TCP hub/ping-server handshakes, TLS/auth variants, WebRTC data-channel
  transport, and WebTransport/HTTP3 QUIC datagrams.
- Why it matters: the current implementation is only a direct UDP DEFAULT audio
  slice, not a full JackTrip connector.
- Runtime/user impact: many public JackTrip deployments, especially hub or web
  modes, will not work.
- Suggested remediation: keep these explicitly out of first-slice runtime. Add
  TCP unauthenticated hub handshake only after direct UDP peer parity is proven.
- Verification required: byte-level handshake fixtures, local TCP server/client
  tests, and explicit unsupported-mode reports until implemented.
- Suggested test: unauthenticated hub client sends 32-bit little-endian bind
  port plus padded name and consumes a server UDP port response.
- Risk of change: high.
- Confidence: high

### JT-06: Bit-depth support is declared broader than payload conversion supports

- Severity: P2
- Category: Codec correctness
- Subsystem: JackTrip sample conversion
- File: `Sources/OpenLolaCore/Connectors/JackTrip/JackTripProtocolModel.swift`,
  `Sources/OpenLolaCore/Connectors/JackTrip/JackTripAudioPayloadCodec.swift`
- Evidence: `JackTripBitResolution` enumerates 8/16/24/32, but conversion helpers
  are `planarInt16Payload` and `interleavedInt16Payload`. Public JackTrip docs
  describe 8-bit signed, 16-bit little-endian, 24-bit non-standard 3-byte, and
  32-bit float payload behavior.
- Why it matters: accepting the enum without implementing all conversions can
  create misleading compatibility claims.
- Runtime/user impact: non-16-bit JackTrip streams are not correctly handled.
- Suggested remediation: either narrow construction to 16-bit only in first
  slice or implement/test each bit-depth conversion.
- Verification required: fixtures for 8/16/24/32-bit payload conversion and
  malformed-length rejection.
- Suggested test: 24-bit decode/encode fixture matching JackTrip's documented
  two-byte plus remainder-byte behavior.
- Risk of change: medium.
- Confidence: high

### JT-07: Stop/control datagram handling is filtered but not reported

- Severity: P2
- Category: Runtime observability
- Subsystem: JackTrip receive
- File: `Sources/OpenLolaCore/Connectors/JackTrip/JackTripCompatibility.swift`
- Evidence: RX ignores a 63-byte all-`0xff` datagram but does not record a stop
  event, shutdown reason, or peer-stopped status.
- Why it matters: public JackTrip documents the stop/control datagram as
  shutdown signaling. Silently ignoring it hides a real state transition.
- Runtime/user impact: a session can time out or appear incomplete instead of
  saying the peer stopped.
- Suggested remediation: add stop-control counters/status and treat stop as an
  explicit terminal receive condition.
- Verification required: receive tests for stop-only, stop-after-audio, and
  malformed all-`0xff` wrong-length datagrams.
- Suggested test: one audio packet followed by stop datagram yields
  `peerStopped == true` and no timeout failure.
- Risk of change: low-medium.
- Confidence: high

### JT-08: QoS / DSCP / macOS voice service marking is missing

- Severity: P2

- Subsystem: JackTrip and shared UDP sockets

- Why it matters: this affects real network behavior, especially campus or WAN

- Runtime/user impact: Open LoLa native JackTrip may not match reference
  JackTrip network treatment.
- Suggested remediation: add opt-in or default-safe socket QoS marking with
  report evidence of attempted/applied/fallback status.
- Verification required: unit-level socket option abstraction tests and manual
  route capture evidence before product claims.
- Suggested test: injected socket option setter records `NET_SERVICE_TYPE_VO`
  attempt on Darwin.
- Risk of change: medium.
- Confidence: medium

## Suggested Implementation Order

1. Strengthen evidence boundaries first.
   - Add explicit payload provenance and peer-evidence fields.
   - Add negative validation tests rejecting `PASS` for synthetic/local-only
     connector evidence.

2. Fix JackTrip DEFAULT correctness before broadening.
   - Implement channel sentinel handling.
   - Add DEFAULT packet fixtures for documented sentinel cases.
   - Keep non-16-bit modes unsupported unless full conversion lands.

3. Implement JackTrip UDP datagram framing.
   - Add single-packet and redundancy datagram codecs.
   - Add stop-control reporting.
   - Add sequence/redundancy recovery tests.

4. Add shared live audio provider integration.
   - Reuse or generalize the LoLa CoreAudio live bridge safely.
   - Keep capture/playback off realtime-critical paths except through existing
     bounded rings/graphs.

5. Add UltraGrid receive analysis.
   - Per-stream SSRC/sequence/timestamp/loss/duplicate/reorder counters.
   - Full-frame reassembly counters and malformed-fragment failures.

6. Replace UltraGrid generated-video shortcut with real configured frame sizes
   and provider injection.
   - Generated full-frame tests first.
   - AVFoundation raw provider after full-frame packetization is stable.

7. Add direct peer socket integration tests.
   - JackTrip P2P endpoint learning.
   - UltraGrid direct peer TX/RX on 5004/5006-compatible ports.

8. Add parity gates against real public tools.
   - Swift-native TX into UltraGrid/JackTrip reference RX.
   - Reference TX into Swift-native RX.
   - Keep verdict `PARTIAL` until field thresholds and route evidence are met.

9. Consider advanced modes only after direct UDP parity is proven.
   - UltraGrid FEC/encryption/codec payloads.
   - JackTrip unauthenticated TCP hub handshake.
   - JackTrip TLS/auth/WebRTC/WebTransport only with explicit product need.

## Bottom Line

The current implementation is a useful first source-level slice:

- UltraGrid: native RTP/MVTP PT 20 raw-video fragments and PT 21 PCM audio.
- JackTrip: native UDP DEFAULT packet header and planar 16-bit PCM.

The missing work for "full connector" status is mostly not about adding another
launch option. It is live media integration, correct peer/network state
machines, receive-quality analysis, documented JackTrip DEFAULT edge cases,
JackTrip redundancy, explicit evidence boundaries, and measured peer parity.

Until those are implemented and measured, both connectors should remain
`PARTIAL` and should be described as native packetization/report surfaces rather
than field-ready UltraGrid or JackTrip replacements.
