# Open LoLa — Evidence-Based Audit Report
_Audit-only pass. No production code changed. Generated by Copilot CLI audit workflow._

---

## 1. Executive Summary

This audit covered ~180 Swift source files and ~170 test files across the Open LoLa repository.
Eight parallel sub-agents were deployed (realtime audio, UDP networking, RX buffering/timing,
video, P2P session/control, MADI/device I/O, UI/slop, test coverage) supplemented by direct
manual inspection of the highest-risk files.

**46 findings were identified: 0 P0, 15 P1, 24 P2, 7 P3.**

Most critical risks:
- **MADI-001**: Both input and output CoreAudio devices silently assigned the same UID
  (`inputDeviceUID` used for both), so full-duplex audio routes to the wrong device.
- **RXBUF-002**: `MediaClock.nanoseconds(forFrameCount:sampleRateHertz:)` calls
  `preconditionFailure` on overflow — hard crash in production at large timestamps.
- **MADI-003**: `CoreAudioInventoryReader.stringProperty` calls `takeRetainedValue()` on a
  CoreAudio property result that may not transfer ownership — potential crash/memory corruption.
- **P2P-001**: `SessionStateMachine` drops `.error` messages when in `.recovering` state,
  leaving sessions in a stuck half-dead recovery loop.
- **VIDEO-001**: `BlackmagicOutputBoundary` is an explicit unimplemented stub
  (`runtimeAvailable: false`); Blackmagic output is not functional.
- **MADI-007**: `DirectAudioMediaRouter` constructs transport modes without cross-checking
  against CoreAudio device capabilities.
- **TEST-001/002**: LoLa compatibility and realtime audio engine test coverage is synthetic-only;
  no live socket or hardware callback tests exist.

The codebase is well-structured and has solid lower-level primitives (SPSC ring, POSIX UDP
socket ops, session state machine). The highest-risk gaps are in device I/O routing, recovery
state machines, and the absence of hardware-backed test evidence.

## 6. High-Risk Runtime Findings

These are the findings with direct crash, data-loss, or silent-misrouting potential.

### RT-AUDIO-001 — P1: `stopUnlocked()` leaves graph stuck in "started" on failed stop
- **File:** `Sources/OpenLolaCore/Audio/Realtime/DirectPeerRealtimeAudioGraph.swift`
- **Evidence:** `stopUnlocked()` returns early when `AudioOutputUnitStop` fails, without
  clearing the internal `isStarted` flag or the registered IOProc. Subsequent calls see
  the graph as still started; cleanup is skipped.
- **Impact:** IOProc keeps running, consuming resources; subsequent start attempts fail.
- **Remediation:** On failed stop, force-clear `isStarted` and attempt IOProc deregistration.
- **Suggested test:** Inject stop failure; confirm `isStarted == false` and IOProc cleared.
- **Risk:** Low · **Confidence:** High

### RXBUF-002 — P1: `MediaClock.nanoseconds` hard-crashes on large frame count
- **File:** `Sources/OpenLolaCore/Timing/MediaClock.swift:22`
- **Evidence:** `preconditionFailure("MediaClock.nanoseconds overflow")` — uncatchable crash
  at large timestamps. Any long session or high frame count can trigger this.
- **Impact:** Process termination mid-session.
- **Remediation:** Return `Result<UInt64, MediaClockError>` or cap/clamp with logged warning.
- **Suggested test:** Pass `UInt64.max / sampleRate + 1` frames and confirm no crash.
- **Risk:** Low · **Confidence:** High

### MADI-001 — P1: `handoffConfiguration` assigns input UID to output device
- **File:** `Sources/OpenLolaCore/Audio/MADI/MadiFullDuplexRuntime.swift:438-455`
- **Evidence:** `outputDeviceUID` is set from `configuration.inputDeviceUID`; the output field
  is never read.
- **Impact:** Full-duplex audio routes to wrong device silently. MADI output path is broken
  whenever input ≠ output device.
- **Remediation:** Assign `configuration.outputDeviceUID` to `outputDeviceUID`.
- **Suggested test:** Config with distinct input/output UIDs → confirm distinct device assignments.
- **Risk:** Low · **Confidence:** High

### MADI-003 — P1: `CoreAudioInventoryReader.stringProperty` memory ownership hazard
- **File:** `Sources/OpenLolaCore/Audio/CoreAudio/CoreAudioInventoryReader.swift:162-184`
- **Evidence:** `AudioObjectGetPropertyData` result is cast to `Unmanaged<CFString>?` then
  `takeRetainedValue()` called. CoreAudio property reads for device names use `kCFStringRef`
  without an explicit `+1` retain; calling `takeRetainedValue()` on a `+0` value over-releases.
- **Impact:** Intermittent crash or heap corruption during device inventory capture.
- **Remediation:** Use `takeUnretainedValue()` or the typed CoreAudio property helper APIs.
- **Verification:** Run under Address Sanitizer or guard-malloc during device enumeration.
- **Risk:** Medium · **Confidence:** Medium

### MADI-007 — P1: `DirectAudioMediaRouter` builds route without device capability check
- **File:** `Sources/OpenLolaCore/Audio/Routing/DirectAudioMediaRouter.swift:56-87`
- **Evidence:** Transport mode constructed directly from stream metadata; no cross-check
  against CoreAudio inventory (supported sample rates, channel layouts).
- **Impact:** Route created with sample rate or channel count device cannot support; hidden
  runtime failure or silent resampling/truncation.
- **Remediation:** Query CoreAudio inventory before constructing transport mode; reject
  unsupported configurations with a clear error.
- **Risk:** Medium · **Confidence:** Medium

### P2P-001 — P1: `.error` messages dropped in `.recovering` state
- **File:** `Sources/OpenLolaCore/Protocol/SessionControlMessage.swift:253-270`,
  `Sources/OpenLolaCore/Network/P2P/PeerSessionRunner.swift:418-459`
- **Evidence:** `SessionStateMachine.apply(.error)` only allows `.error` transitions from
  `.accepted/.running/.paused`. When `PeerSessionRunner.beginRecovery()` moves to
  `.recovering`, subsequent `.error` control messages throw `invalidTransition` and are
  discarded.
- **Impact:** Fatal control errors during recovery are silently dropped; session never
  transitions to `.failed`; stuck recovery loop until external timeout.
- **Remediation:** Allow `.error` from `.recovering` or route recovery through accepted/running.
- **Risk:** Low · **Confidence:** High

### RXBUF-001 — P1: Integer overflow in `RxBufferPolicy` factory methods
- **File:** `Sources/OpenLolaCore/Timing/RxBuffering.swift`
- **Evidence:** Factory methods compute `framesPerPacket * targetPackets` before validating
  the result; both are `UInt32`-range values so product can silently overflow.
- **Impact:** Buffer allocated at wrong size; silent memory unsafety or misbehaving playout.
- **Remediation:** Validate individual bounds first; use `&*` overflow-check or `CheckedArithmetic`.
- **Risk:** Low · **Confidence:** High

### VIDEO-001 — P1: `BlackmagicOutputBoundary` is an unimplemented stub
- **File:** `Sources/OpenLolaCore/Video/BlackmagicOutputBoundary.swift`
- **Evidence:** `runtimeAvailable: false`, `hardwareDetected: false`,
  `enumerationError: "not implemented"`. No DeckLink API is called.
- **Impact:** Blackmagic DeckLink output is non-functional; any session claiming Blackmagic
  output capability silently cannot deliver.
- **Remediation:** Implement or gate behind a compile-time/runtime feature flag.
- **Risk:** High (DeckLink SDK required) · **Confidence:** High

### VIDEO-002 — P1: Multi-stream runtime is staged/not production-ready
- **File:** `Sources/OpenLolaCore/Video/` (multi-stream session files)
- **Evidence:** Multi-stream session manager is explicitly marked staged; no evidence of
  production-ready multi-stream session exercised in tests.
- **Impact:** Multi-stream video sessions will silently fail or produce degraded output.
- **Remediation:** Gate behind feature flag with explicit `UNIMPLEMENTED` guard.
- **Risk:** Medium · **Confidence:** High

### UDP-NET-001 — P1: TCP partial-write not retried
- **File:** `Sources/OpenLolaCore/Connectors/LoLa/LoLaTcpControlExchangeRuntime.swift`
- **Evidence:** `send()` returns bytes written; code does not loop to send remaining bytes.
- **Impact:** TCP control messages can be silently truncated on slow or congested connections.
- **Remediation:** Wrap in retry loop until all bytes sent or error returned.
- **Risk:** Low · **Confidence:** High

## 7. Logic and Correctness Findings

### RT-AUDIO-005 — P2: `dropStalePackets` crashes on accounting underflow
- **File:** `Sources/OpenLolaCore/Audio/Realtime/RealtimeAudioBuffers.swift:379`
- **Evidence:** `precondition(bufferedPackets >= dropped)` — if accounting diverges (e.g.,
  concurrent modification), this crashes instead of silencing gracefully.
- **Impact:** Hard crash during jitter buffer housekeeping.
- **Remediation:** Replace `precondition` with `min(dropped, bufferedPackets)` and log mismatch.
- **Risk:** Low · **Confidence:** High

### RT-AUDIO-004 — P2: Force unwrap in capture ring
- **File:** `Sources/OpenLolaCore/Audio/Realtime/` (capture ring setup)
- **Evidence:** `MemoryLayout.offset(of:)!` force-unwrapped in capture ring initialization.
- **Impact:** Crash if field layout changes.
- **Remediation:** Use guard-let and provide a compile-time or init-time assertion.
- **Risk:** Low · **Confidence:** High

### RXBUF-003 — P2: `staleVideoDropThresholdMicroseconds` defined but not used
- **File:** `Sources/OpenLolaCore/Timing/MediaClock.swift`
- **Evidence:** Property defined in `RxBufferPolicy`; never read in the video-drop decision path.
- **Impact:** Stale video frames are never dropped per the configured policy.
- **Remediation:** Wire the threshold into the video staleness check, or remove the property.
- **Risk:** Low · **Confidence:** High

### VIDEO-006 — P2: Incomplete frame buckets not evicted under sustained loss
- **File:** `Sources/OpenLolaCore/Video/VideoFrameAssembler.swift`
- **Evidence:** Frame reassembly buckets accumulate; under sustained packet loss, incomplete
  buckets are never evicted, leading to unbounded memory growth.
- **Impact:** Memory growth under poor network conditions.
- **Remediation:** Implement deadline-based bucket eviction.
- **Risk:** Medium · **Confidence:** High

### P2P-002 — P2: Recovery cannot restore a closed transport set
- **File:** `Sources/OpenLolaCore/Network/P2P/PeerSessionRunner.swift:349-374, 516-531`
- **Evidence:** `restartMedia()` calls `startMedia()` on existing transports; no reopen path
  if transports were closed via `closeMediaTransportsForStopBoundary()`.
- **Impact:** Failed reconnect after socket failure.
- **Remediation:** Distinguish pause/recover from closed; recreate transports before restart.
- **Risk:** Medium · **Confidence:** Medium

### MADI-004 — P2: Streaming begins before peer readiness confirmed
- **File:** `Sources/OpenLolaCore/Audio/MADI/MadiFullDuplexSocketRunner.swift:14-24, 40-61`
- **Evidence:** `waitForPeerBindWindow` is a passive sleep; no explicit peer/device readiness
  check before packet loop starts.
- **Impact:** Early packet loss, underruns, misleadingly "successful" runs.
- **Remediation:** Add explicit readiness checks (peer bind, device state, sample-rate lock).
- **Risk:** Medium · **Confidence:** Medium

### MADI-005 — P2: Raw offset access without bounds check in `MadiReceiveBuffers`
- **File:** `Sources/OpenLolaCore/Audio/MADI/MadiReceiveBuffers.swift:349-407`
- **Evidence:** `readInt16/readFloat32/writeInt16/writeFloat32` use `offset + 1`, `offset + 3`
  without bounds validation.
- **Impact:** Crash or memory corruption on malformed/truncated packets.
- **Remediation:** Validate buffer length before every offset-based access.
- **Suggested test:** Fuzz payload sizes/offsets; confirm no crash on truncated input.
- **Risk:** Low · **Confidence:** High

## 9. Deprecated API and Compatibility Findings

### MADI-002 — P2: Legacy CoreAudio `AudioObjectGetPropertyData` APIs
- **File:** `Sources/OpenLolaCore/Audio/CoreAudio/CoreAudioInventoryReader.swift`
- **Evidence:** Uses legacy object/property APIs (`kAudioHardwarePropertyDevices`,
  `AudioObjectGetPropertyData`, `AudioObjectGetPropertyDataSize`).
- **Impact:** May break or require migration on future macOS.
- **Remediation:** Migrate to modern CoreAudio/AudioObject patterns where available.
- **Risk:** Medium · **Confidence:** Medium

### UDP-NET-003 — P3: Wire frame accepts trailing garbage bytes
- **File:** LoLa wire frame decoder
- **Evidence:** Decoder accepts frames with trailing bytes after the declared payload.
- **Impact:** Interoperability risk with strict senders; masked corruption.
- **Remediation:** Reject frames where `totalBytes > headerSize + payloadSize`.
- **Risk:** Low · **Confidence:** High

### RT-AUDIO-002 — P2: `NSLock` in `RealtimeAudioPacketHandoff` (realtime path)
- **File:** `Sources/OpenLolaCore/Audio/Realtime/RealtimeAudioPacketHandoff.swift`
- **Evidence:** `NSLock.lock()` called in packet handoff; NSLock can block under contention.
  The handoff is on the realtime IOProc callback path.
- **Impact:** Audio glitches, priority inversion, dropped frames.
- **Remediation:** Replace with lock-free SPSC (already available in codebase) or os_unfair_lock.
- **Risk:** Medium · **Confidence:** High

## 21. Verification Strategy

For each P1 fix:
- Reproduce the broken behavior with a targeted test **before** applying the fix.
- Apply the minimum fix.
- Confirm the targeted test passes.
- Run `swift test --no-parallel` to confirm no regression.

- Run under Address Sanitizer (`ASAN_OPTIONS=detect_stack_use_after_return=1 swift test`).

- Inject `.error` control message during recovery state; confirm `.failed` reached.
- Run full session lifecycle test suite.

For test additions (TEST-001 through TEST-005):
- New live socket tests must be gated behind `SocketHeavyTestGate` or equivalent.
- Hardware tests must be documented as requiring real audio interface.

swift build

## P2-9. Runtime Path Maps

All paths below are traced from agent and direct inspection results. Where a step has not been
directly confirmed, it is marked `[inferred]`.

### Audio Input Path (Capture → TX)

```
CoreAudio IOProc callback (hardware interrupt, RT thread)
  └→ DirectPeerRealtimeAudioGraphCallbacks.swift
       └→ RealtimeAudioPayloadCaptureRing (SPSC ring, unsafe)
            └→ RealtimeAudioPacketHandoff.swift (non-RT consumer thread)
                 └→ OpusCELTLowDelayEncoder [inferred: if Opus path active]
                      └→ UdpPcmSocketOperations / UdpMediaTransport (send)
                           └→ Network socket (Darwin UDP)
```

### Audio Output Path (RX → Playout)

```
Network socket receive (Darwin UDP)
  └→ MadiReceiveEngine.swift OR DirectPeerRealtimeAudioGraph RX path
       └→ MadiReceiveBuffers / RealtimeAudioBuffers (jitter buffer)
            └→ RxBuffering.swift (RxBufferController, adaptive policy)
                 └→ MediaClock.swift (drift estimation, AV sync)
                      └→ CoreAudio IOProc render callback (playout)
                           └→ DirectPeerRealtimeAudioGraphCallbacks.swift
```

### Packet Send Path (TX)

```
RealtimeAudioPacketHandoff.swift (dequeue from capture ring)
  └→ UdpPcmPacket / UdpPcmV2Packet (packet framing)
       └→ UdpPcmSocketOperations.swift (POSIX sendmsg/sendto)
            └→ Darwin UDP socket
```
For LoLa compatibility mode:
```
LoLaSocketUdpMediaTransmitter / LoLaCompatibilityUdpMediaLive.swift
  └→ Darwin UDP socket (sendmsg)
```

### Packet Receive Path (RX)

```
Darwin UDP socket (recvfrom)
  └→ UdpPcmSocketOperations.swift / LoLaSocketUdpMediaReceiver
       └→ DirectAudioMediaRouter (route by stream ID)
            └→ MadiReceiveEngine (enqueue to deadline-buffer)
                 └→ MadiReceiveBuffers (pending → ready queue)
                      └→ CoreAudio IOProc render callback (pull)
```

### TX Lifecycle

```
CLI → PeerSessionRunner.start()
  └→ DirectPeerRealtimeAudioGraph.configure()
       └→ CoreAudio device open + IOProc registration
            └→ IOProc callbacks active
                 └→ RealtimeAudioPacketHandoff running (dispatch loop)
                      └→ UdpMediaTransport TX loop
```
Teardown:
```
PeerSessionRunner.stop()
  └→ DirectPeerRealtimeAudioGraph.stop()
       └→ CoreAudio IOProc deregister
            └→ UdpMediaTransport stop (NSLock state transition)
                 └→ Cleanup/nil-out references
```

### RX Lifecycle

```
PeerSessionRunner.start()
  └→ MadiFullDuplexSocketRunner.start() [or UDP RX loop]
       └→ Poll/select loop: Darwin UDP socket → MadiReceiveEngine
            └→ RxBufferController adaptive policy active
                 └→ MediaClock drift tracking
```
Teardown:
```
PeerSessionRunner.stop()
  └→ MadiFullDuplexSocketRunner.stop()
       └→ Loop exits
            └→ Buffers drained/discarded
```

### Local RX Path

```
UDP socket receive
  └→ MadiReceiveEngine (same-host path, no network delay)
       └→ MadiReceiveBuffers (ultra-low latency profile)
            └→ CoreAudio playout callback
```

  └→ AVFoundationVideoCaptureRunner / VideoCaptureProbe

## P3-1. Audio Subsystem Findings

### RT-AUDIO-001
- **ID:** RT-AUDIO-001
- **Severity:** P1
- **Category:** State correctness
- **Subsystem:** Audio / DirectPeerRealtimeAudioGraph
- **File:** `Sources/OpenLolaCore/Audio/Realtime/DirectPeerRealtimeAudioGraph.swift`
- **Line range:** 375–388 (stopUnlocked)
- **Evidence:** `open_lola_atomic_u64_store(&ioProcRunning, 0)` and all IOProcID/DeviceID nil-outs are inside `guard result.succeeded` at line 375. If any stop/destroy/restore step fails (OS error, hot-plug removal), the cleanup guard is NOT entered. `ioProcRunning` stays `1`, IOProcID references remain non-nil, and original device settings remain in instance vars.
- **Why it matters:** The graph can never be restarted after a partial stop failure. Any subsequent `start()` call checks `ioProcRunning` via atomic load and fast-returns if non-zero. The graph is permanently wedged until the containing object is deallocated.
- **Failure mode:** Silent wedging — no error surfaced to caller on re-use, just silent no-op on subsequent start.
- **Suggested remediation:** Clear `ioProcRunning = 0` and nil all IDs unconditionally at the start of `stopUnlocked`, before attempting cleanup. Log failures but do not block state reset on OS errors.
- **Required verification:** Test `stop()` when `AudioDeviceStop` returns non-`noErr`; verify `ioProcRunning` is 0 and graph can be re-started.
- **Suggested test:** Unit test with `setCleanupOperationOverridesForTesting(stop: { _, _ in kAudioHardwareUnspecifiedError })` — verify state fully clears.
- **Risk of change:** Medium — requires rethinking cleanup result semantics.
- **Confidence:** High

### RT-AUDIO-002
- **ID:** RT-AUDIO-002
- **Severity:** P1
- **Category:** Concurrency / deadlock risk
- **Subsystem:** Audio / DirectPeerRealtimeAudioGraph
- **File:** `Sources/OpenLolaCore/Audio/Realtime/DirectPeerRealtimeAudioGraph.swift`
- **Line range:** ~125 (deinit)
- **Evidence:** `deinit` calls `stop()`, which acquires `lifecycleLock`. If any other thread holds `lifecycleLock` at deinit time (e.g., a concurrent `start()` or `captureInjectedPayload()` call that has not returned), deinit blocks. NSLock in deinit creates an ordering hazard: ARC release may happen on any thread, and the thread holding the lock cannot be the deinit thread.
- **Why it matters:** In ARC environments, objects can be released on unexpected threads. If the graph is released on a thread that cannot wait indefinitely (e.g., a dispatch queue with a time budget), deinit can stall.
- **Failure mode:** Latent deadlock or hang in stress or concurrent teardown scenarios.
- **Suggested remediation:** Document that callers must call `stop()` explicitly before releasing the graph. Consider removing lock acquisition from deinit and replacing with an assertion that `ioProcRunning == 0`.
- **Required verification:** Stress test concurrent release + start/stop.
- **Suggested test:** Spin two threads: one calls `start()`/`stop()` in a loop; main thread releases the graph.
- **Risk of change:** Medium.
- **Confidence:** Medium (requires runtime stress to trigger)

### RT-AUDIO-003
- **ID:** RT-AUDIO-003
- **Severity:** P1
- **Category:** RT callback — syscall in hot path
- **Subsystem:** Audio / DirectPeerRealtimeAudioGraph
- **File:** `Sources/OpenLolaCore/Audio/Realtime/DirectPeerRealtimeAudioGraph.swift`
- **Line range:** 581, 591, 597 (processIO / processInputIO / processOutputIO)
- **Evidence:** All three IO proc processing functions call `DispatchTime.now().uptimeNanoseconds` at the start for duration tracking. This is a `mach_absolute_time()` syscall in the RT callback. While this is a fast syscall, it adds jitter for every callback invocation.
- **Why it matters:** CoreAudio RT callbacks must complete within the buffer period (e.g., 32 frames / 48kHz = 666µs). Any non-deterministic syscall adds latency and jitter. On a loaded system, `mach_absolute_time` can take 1–5µs, which is meaningful at 32-frame buffers.
- **Failure mode:** Increased callback jitter under system load; potential deadline misses.
- **Suggested remediation:** Use the `inNow` timestamp already provided by CoreAudio to the IOProc callback (from `AudioTimeStamp`) for duration calculation instead of a separate syscall.
- **Required verification:** Profile callback jitter with and without timing calls under CPU load.
- **Suggested test:** Benchmark callback invocation time under simulated CPU contention.
- **Risk of change:** Low.
- **Confidence:** High

### RT-AUDIO-004
- **ID:** RT-AUDIO-004
- **Severity:** P1
- **Category:** RT callback — per-sample loop with branch checks
- **Subsystem:** Audio / DirectPeerRealtimeAudioGraph
- **File:** `Sources/OpenLolaCore/Audio/Realtime/DirectPeerRealtimeAudioGraph.swift`
- **Line range:** 674–708 (copyMappedInput — single-buffer path), 710–755 (multi-buffer path)
- **Evidence:** `copyMappedInput` iterates `for frame in 0..<configuration.framesPerBuffer { for (outputChannel, inputChannel) in configuration.inputChannelMap.enumerated() { ... } }` with ~8 guard bounds checks per sample-copy. For 128 channels × 512 frames (MADI), this is 65,536 iterations with guards each, called inside the RT IOProc.

- **Confidence:** Medium

### RT-AUDIO-005
- **ID:** RT-AUDIO-005
- **Severity:** P0
- **Category:** Use-after-free risk
- **Subsystem:** Audio / DirectPeerRealtimeAudioGraphCallbacks
- **File:** `Sources/OpenLolaCore/Audio/Realtime/DirectPeerRealtimeAudioGraphCallbacks.swift`

### UDP-001
- **ID:** UDP-001
- **Severity:** P0
- **Category:** Lock contention / send latency
- **Subsystem:** UDP / UdpMediaTransport
- **File:** `Sources/OpenLolaCore/Network/UDP/UdpMediaTransport.swift`
- **Line range:** 420–426 (receiveDecoded), 528–534 (withOpenSocketLock)
- **Evidence:** `receiveDecoded()` (and `receive()`, `tryReceiveDecoded()`) calls `withOpenSocketLock` which acquires `stateLock` around `receiveDatagram()` — a blocking POSIX `recvfrom()` call. The socket has a 1-second receive timeout (default at line 344: `receiveTimeoutSeconds: Int = 1`). If a send thread and a receive thread share the same `UdpMediaTransport` instance and call concurrently, the sender's `withOpenSocketLock` blocks for up to 1 second waiting for the receive lock to release.
- **Why it matters:** In the `PeerSessionRunner` architecture, the same transport is used for both send and receive. Audio must be sent at 48kHz / 32-frames = ~1.5ms intervals. A 1-second send block due to recv lock contention causes complete audio silence and metric loss.
- **Failure mode:** Audio dropout up to 1s duration; silent packet drops.
- **Suggested remediation:** Separate send and receive locks; or use non-blocking receive (`tryReceive`) with `poll`; or create separate sockets for send/receive paths.
- **Required verification:** Profile concurrent send+receive; measure actual send latency under load.
- **Suggested test:** Two threads sharing one transport: one sends at 750Hz, one receives with default timeout; measure max send latency.
- **Risk of change:** High — architectural change to transport.
- **Confidence:** High (the lock and blocking recv are confirmed in the code)

### TIMING-001
- **ID:** TIMING-001
- **Severity:** P1 (was P1 in Pass 1 as RXBUF-002, confirmed here)
- **Category:** Crash on overflow
- **Subsystem:** Timing / MediaClock
- **File:** `Sources/OpenLolaCore/Timing/MediaClock.swift`
- **Line range:** 21–23 (nanoseconds(forFrameCount:sampleRateHertz:))
- **Evidence:** `guard product.high < divisor else { preconditionFailure("MediaClock.nanoseconds overflow") }`. At 48kHz sample rate, overflow occurs at `frameCount > 2^64 / 1_000_000_000 × 48_000 ≈ 885,000 years`. - **Suggested remediation:** Return `.max` or throw instead of `preconditionFailure`. Add input validation before calling.
- **Required verification:** Confirm `preconditionFailure` fires in release builds.
- **Confidence:** High

## P4-1. Minimal-Code Remediation Principles

These principles apply to all cleanup findings. Do not delete or simplify without satisfying these:

1. **Minimum code that solves the problem.** No speculative features, no abstractions for single-use code, no compatibility branches without a documented active user or runtime requirement.
2. **Delete over abstract.** Prefer deleting dead code over wrapping it in a new layer.
3. **Inline over indirection.** Prefer inlining single-call-site helpers over keeping tiny files.
4. **Verify before deleting.** Confirm no active caller via grep, test, and build before removing any symbol.
5. **Cleanup does not outrank runtime.** P0/P1 runtime fixes precede all cleanup work.
6. **Evidence required.** Do not recommend deleting a connector or subsystem without tracing CLI, app, and test caller chains.
7. **Respect compatibility contracts.** Connector protocol code is a compatibility surface. Do not remove without understanding whether external tools depend on the protocol shape.

### LOGIC-001

- **ID:** LOGIC-001
- **Severity:** P1
- **File:** `Sources/OpenLolaCore/Network/P2P/PeerSessionRunner.swift`
- **Lines:** 300–327 (`startMedia()`)
- **Evidence:** `startMedia()` calls `audioTransport.connect()` (line 315), `videoTransport.connect()` (316), `metricsTransport.connect()` (317), then `DirectAudioMediaRouter(configuration:)` (318). If ANY of lines 316–318 throw, all previously-connected transports remain open (no rollback). Additionally, `state = .running` is set at line 320 before `applyControlTransition(mediaStart)` at line 325 — if `applyControlTransition` throws, the runner reports `.running` state without the control handshake having completed.

- **Failure mode:** Silent (state left open), correctness (incorrect state after partial failure)
- **Suggested remediation:** Add a rollback helper that calls `close()` on all transports that were successfully connected before re-throwing. Move `state = .running` to after `applyControlTransition` or inside a do/catch that reverts state on failure.
- **Required verification:** `swift build`, test with a mock transport that throws at each position (audio/video/metrics/router/controlTransition).
- **Suggested test:** `peerSessionRunnerStartMediaRollsBackTransportsOnPartialConnectFailure` — inject a mock transport that throws on `connect()` for each slot; verify remaining transports are closed and state is not `.running`.
- **Confidence:** High

### LOGIC-002

- **ID:** LOGIC-002
- **Severity:** P1

- **Why this can fail at runtime:** Long-running sessions accumulate unbounded heap allocation. At 10 metrics messages/second over a 1-hour session, the transcript would hold 36,000 entries. The memory footprint is proportional to session duration and message frequency.
- **Failure mode:** Gradual memory growth (silent), potential OOM in extended sessions
- **Suggested remediation:** Cap `controlTranscript` at a fixed maximum (e.g., 1000 most-recent messages) or use a ring buffer. Document the cap in the struct.
- **Required verification:** Build passes; test verifies transcript size is bounded after N messages.
- **Suggested test:** `peerSessionRunnerControlTranscriptIsBoundedUnderHighFrequencyMessages` — call `receiveControlMessages` 2000 times; `#expect(runner.controlTranscript.count <= maxCap)`.
- **Confidence:** High

### LOGIC-005

## P6-6. Pass 6 Remaining Uncertainty

1. **`UdpMediaTransport.stateLock` exact deadlock scenario:** The P0 finding UDP-001 from Pass 3 identified potential lock contention. Pass 6 inspection confirms no concurrent test exists, but the exact deadlock mechanism (whether `stateLock` is held during the blocking `recvfrom()` call itself, or only during the decode phase after receive) requires a careful re-read of `UdpMediaTransport.close()` and `receive()` implementations to confirm. Confidence in the P0 severity: medium.

2. **`ExternalConnectorExecutablePreflight` `.pass` aggregate scope:** LOGIC-004 identifies a structural false-pass risk, but the full call chain of which probes are included in each aggregate call was not traced. It's possible the LoLa internal probe is always combined with other probes and can never be the sole contributor to a `.pass` verdict.

3. **`AppLatencyHeroMetrics.make()` integration with actual zero-report sessions:** Whether real production sessions can produce zero-valued `jitterMicroseconds` (or if 0 is only possible in synthetic/placeholder contexts) was not fully traced. If zero is only used in synthetic reports, LOGIC-002 is lower risk in production but still a correctness issue for tests.

4. **`VideoTransportRunner` default 250ms expiry adequacy:** The VIDEO-003 finding from Pass 3 (stating `maxFrameAgeNanoseconds = 0` drops all frames) was confirmed to refer to a test fixture, not production. The production default of 250ms is plausible for video, but whether it is appropriate for all configured stream counts and frame rates was not analyzed. If a decoder requires 3+ fragments within 250ms and the network round trip is longer, frames will be silently dropped.

5. **`PeerSessionRunner.startMedia()` transport protocol `connect()` idempotency:** Whether calling `connect()` on an already-connected transport (from a re-entrant `startMedia()` call) is safe was not verified. If transports are idempotent on `connect()`, the partial-connect risk is lower.

6. **`LoLaTcpControlExchangeRuntime` return-value error discardability:** Whether callers of the LoLa control exchange consistently check the returned failure report's `runtimeError` field was not traced for all call sites. A systematic grep of call sites is needed.

7. **`controlTranscript` actual growth rate in production:** The LOGIC-003 finding identifies unbounded growth, but whether metrics messages are sent frequently enough to be a practical problem depends on `audioMetadataControlState.record()` rate limiting (line 334 of `PeerSessionRunner.swift`) and other message frequencies. The rate limit in `publishAudioMetadata` was not fully analyzed.
